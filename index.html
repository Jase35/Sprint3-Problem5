3. When running time becomes a secret leak

A side channel is information that escapes through how a computation runs rather than what it returns. The classic example is a password/token comparison that stops at the first wrong character: the more characters you get right, the longer the check takes. That tiny timing difference turns a O(kn) brute-force problem into a O(k·n) stroll.

This is a simulation. Timings are generated from a cost model (one comparison ≈ 12 ns) plus random jitter, so the lesson is reproducible and nothing on your machine is attacked or measured.

4. Writing code that does not leak

❌ Leaks timing

function unsafeEqual(a, b) {
  if (a.length !== b.length) return false;
  for (let i = 0; i < a.length; i++) {
    // returns early -> run time
    // depends on the secret
    if (a[i] !== b[i]) return false;
  }
  return true;
}

✅ Constant time

function safeEqual(a, b) {
  if (a.length !== b.length) return false;
  let diff = 0;
  for (let i = 0; i < a.length; i++) {
    // always touches every byte
    diff |= a.charCodeAt(i) ^ b.charCodeAt(i);
  }
  return diff === 0;
}
  • Use vetted primitives. crypto.timingSafeEqual (Node), hmac.compare_digest (Python), subtle.ConstantTimeCompare (Go).
  • Compare hashes, not raw secrets. Comparing HMACs of both values means a leaked prefix tells the attacker nothing useful.
  • Make control flow secret-independent. No branches, early returns, table lookups, or memory accesses driven by secret data.
  • Rate-limit and alert. The attack needs thousands of near-identical requests — that is detectable.
  • Remember the other channels. Power draw, cache behavior (Spectre/Meltdown), EM emissions, compression size (CRIME/BREACH), and even error-message wording all leak.
